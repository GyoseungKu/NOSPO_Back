# NOSPO 프로젝트 개발 규약

버전: 1.0 · 작성일: 2026-11-06

## 1. 문서의 목적

이 문서는 NOSPO를 개발하는 팀원이 함께 지킬 서비스 정책과 설계 원칙을 정리한다. 특정 개발 도구나 작업자에게 명령하는 문서가 아니라, 기능을 추가하거나 코드를 검토할 때 판단 기준으로 사용하는 문서다.

서비스의 동작, 기능별 책임, 모듈 사이의 관계를 중심으로 설명한다. 개별 API의 경로·필드·오류 코드는 별도 API 명세서에서 관리하며, 이 문서에 전문을 중복해서 넣지 않는다.

| 문서 | 확인할 내용 |
| --- | --- |
| 이 문서 | 어떤 서비스를 만들며, 어떤 원칙으로 개발하는가 |
| [API 명세서 v2.0](https://chatgpt.com/library?file_id=libfile_d08c56d525a48191acd6b59462d5766c&account_id=personal) | 요청·응답·권한·처리 규칙의 상세 계약 |
| [API 요약 엑셀](https://chatgpt.com/library?file_id=libfile_149326f9fdf88191b6c5a47fa28dd7e8&account_id=personal) | 기능별 API 목록을 빠르게 확인 |

문서 간 내용이 충돌하면 구현자가 임의로 선택하지 않고 팀에서 기준을 정한 뒤 관련 문서를 함께 수정한다.

## 2. 서비스가 제공하는 것

NOSPO는 사용자가 읽은 범위 안에서 도서의 인물·단체·관계를 확인하고, AI에게 질문하거나 관계도를 생성할 수 있는 독서 지원 서비스다. 사용자가 작성한 위키는 관리자 검수를 거쳐 공개하며, 승인된 기여에는 AI 이용 토큰을 보상할 수 있다.

| 기능 영역 | 주요 기능 |
| --- | --- |
| 계정 | 이메일·카카오 가입과 로그인, 로그인 방식 연결, 비밀번호 관리 |
| 회원 정보 | 닉네임·연락처·프로필·이메일 관리, 회원 탈퇴 |
| 약관·공지 | 약관 조회·동의·재동의, 공지사항 조회 |
| 도서·서재 | 도서 검색, 판본별 등록, 개인 서재 관리 |
| 독서 기록 | 현재 진도·최고 진도, 독서량·달력·기간별 활동 |
| 위키 | 인물·단체·관계 조회, 초안 작성·수정, 이미지 관리 |
| 검수 | 제출·수정 요청·재제출·승인·반려, 기여 보상 |
| AI | 질문과 답변 스트리밍, 대화 보관, 관계도 생성·재생성 |
| AI 토큰 | 잔액·예약·사용·지급·회수·복구 이력 |
| 관리자 | 위키 검수, 공지·약관 관리, 토큰 조정 |

## 3. 반드시 일관되게 적용할 서비스 정책

### 3.1 회원과 인증

- 실명은 수집하지 않는다. 휴대전화번호는 필수로 수집하지만 문자 인증은 하지 않는다.
- 휴대전화번호를 본인 인증이나 계정 복구의 근거로 사용하지 않는다.
- 이메일 가입과 카카오 가입을 지원하며, 가입 완료 후 자동 로그인한다.
- 이메일과 카카오 로그인을 하나의 회원 계정에 연결할 수 있다. 이메일이 같다는 이유로 자동 연결하지 않으며, 기존 계정 재인증과 연결 대상 인증을 거친다.
- 카카오 전용 회원은 이메일 인증과 비밀번호 설정을 통해 이메일 로그인을 추가할 수 있다.
- 비밀번호는 Argon2id로 해시하여 저장한다. 변경·재설정 완료 시 기존 로그인 세션을 모두 폐기한다.
- 로그아웃한 세션의 토큰은 유효기간이 남아 있어도 사용할 수 없어야 한다.
- 기존 두 회원 계정의 데이터 병합과 로그인 방식 연결 해제는 현재 범위에 포함하지 않는다.

### 3.2 도서와 독서 기록

- 일반 도서는 외부 도서 검색 API를 사용한다. 웹소설은 카카오페이지·문피아 등의 인기 판타지 작품을 대상으로 사전 구성한 임시 메타데이터를 사용한다.
- 같은 작품이라도 판본이 다르면 별도 도서로 취급한다. 진도·위키·AI 대화와 결과를 판본 간 자동 공유하지 않는다.
- 일반 도서는 페이지, 웹소설은 화를 진도의 기준으로 사용한다. 권·챕터는 현재 위치를 설명하는 구간 정보로 표시한다.
- 독서량은 기존 최고 진도를 넘어선 증가분만 집계한다. 회독 수와 재독 분량은 집계하지 않는다.
- 최초 등록 시 입력한 지점은 이미 읽은 분량으로 보고 당일 독서량에 포함하지 않는다.
- 서재에서 삭제해도 독서 기록과 최고 진도는 유지한다. 재등록으로 이미 집계한 분량이 다시 쌓이지 않아야 한다.
- 페이지와 화는 별도로 집계하며, 날짜별 통계는 한국 시간 기준으로 제공한다.

예를 들어 최고 진도가 40화인 사용자가 30화로 돌아갔다가 45화까지 읽으면, 새롭게 집계되는 독서량은 5화다.

### 3.3 위키와 스포일러 제한

- 위키와 AI 기능은 로그인 후 해당 판본을 서재에 등록한 사용자에게 제공한다.
- 정보 공개 범위는 서버에 저장한 현재 진도를 상한으로 삼는다. 최고 진도까지 읽은 적이 있어도 현재 진도가 낮아지면 이후 정보는 다시 숨긴다.
- 인물의 이름·설명·이미지뿐 아니라 관계의 변화와 종료 정보에도 공개 지점을 적용한다.
- 미래 항목의 존재, 이름, 개수, 이미지 주소 등을 통해 내용이 유추되지 않도록 한다.
- 스포일러 제한은 화면에서만 숨기는 방식이 아니라 서버의 조회·AI 입력·파일 접근 단계에서 적용한다.

### 3.4 위키 작성과 검수

- 편집은 초안에 적용하며, 관리자 승인 전에는 공개 위키가 바뀌지 않는다.
- 검수에 제출한 내용은 고정한다. 이후 수정은 별도 초안과 재제출로 관리한다.
- 인물의 소속과 단체의 구성원은 동일한 관계 데이터로 관리한다.
- 인물 간, 단체 간, 인물과 단체 간 관계를 지원한다.
- 수정의 기준이 된 공개 위키 버전을 기록한다. 다른 수정이 먼저 승인되어 충돌하면 해결한 후 승인한다.
- 승인과 기여 보상이 서로 어긋나거나 중복 처리되지 않도록 한다.

### 3.5 AI와 이용 토큰

| 항목 | 정책 |
| --- | --- |
| 신규 가입 | 5토큰 지급 |
| 자연어 질문 | 질문 1건당 1토큰 |
| 관계도 생성·재생성 | 각각 1건당 1토큰 |
| 기존 결과 조회 | 무료 |
| 시스템 처리 실패 | 차감하지 않음 |
| 위키 승인 보상 | 관리자가 규칙에 따라 수량과 사유 지정, 0토큰 허용 |

- AI는 해당 판본의 승인된 위키 중 조회 지점까지 공개된 정보를 사용한다.
- 질문 답변은 스트리밍으로 제공하고, 관계도는 작업을 접수한 후 상태와 결과를 조회하는 방식으로 제공한다.
- 요청 시 사용할 토큰을 예약하고 정상 완료 시 차감한다. 실패하면 예약을 해제한다.
- 연결 끊김이나 요청 재전송만으로 중복 작업·중복 차감이 발생하지 않아야 한다.
- 근거 부족을 안내하는 정상 답변과 시스템 실패는 구분한다. 정상 답변은 이용 비용을 적용한다.
- 기존 대화와 관계도도 현재 진도에 맞춰 접근을 제한한다.
- 로그인 방식 추가나 계정 연결을 신규 가입으로 취급하여 기본 토큰을 다시 지급하지 않는다.

### 3.6 회원 탈퇴

- 탈퇴 시 개인정보와 개인 데이터를 즉시 삭제하며, 복구 기능을 제공하지 않는다.
- 이미 승인된 공용 위키는 작성자 연결과 식별 정보를 제거한 뒤 유지한다.
- 개인을 식별하거나 다시 연결할 수 없는 최소 운영 로그만 보관한다.
- DB뿐 아니라 파일·캐시·색인·작업 이벤트·복구 가능한 백업 사본까지 삭제 정책의 적용 범위로 본다.
- 진행 중이던 AI 작업 등이 탈퇴 후 개인 데이터를 다시 생성하지 못하도록 한다.
- 삭제가 끝나지 않았으면 탈퇴 성공으로 처리하지 않는다. 실패한 삭제는 접근 차단 상태에서 재처리한다.

## 4. 시스템 구성

백엔드는 Java와 Spring Boot를 사용하며, Gradle 멀티모듈로 구성한다. 업무별 코드 경계를 유지하면서 필요한 기능을 실행 애플리케이션에 조립한다.

| 구성 | 책임 |
| --- | --- |
| API 서버 | 사용자·관리자 요청 처리, 인증, 조회·수정, AI 작업 접수, 답변 스트리밍 전달 |
| AI worker | 오래 걸리는 AI 작업 실행, 답변·관계도 생성, 완료·실패 처리 |
| 관계형 DB | 회원·도서·위키·진도·토큰·작업 등 영속 데이터 저장 |
| 외부 연동 | 카카오, 이메일 발송, 도서 검색, LLM, 파일 저장소 |

모듈은 코드의 책임을 구분하는 단위이며, 서버는 실행·배포 단위다. 각 업무 모듈을 모두 별도 서버로 만들지는 않는다. 초기 DB는 하나를 사용하되 데이터 소유권을 구분한다.

## 5. 업무별 모듈과 책임

| 모듈 | 책임 | 구분할 사항 |
| --- | --- | --- |
| identity | 이메일·비밀번호·카카오 연결·인증 증명·로그인 세션 | 로그인에 필요한 정보와 인증 처리 소유 |
| member | 닉네임·전화번호·프로필·회원 상태 | 서비스 이메일과 비밀번호를 중복 소유하지 않음 |
| terms | 약관 버전·시행·회원 동의 이력 | 약관 본문 변경은 새 버전으로 관리 |
| catalog | 작품·판본·외부 검색·웹소설 구성·검색 이력 | 특정 회원의 독서 진도는 관리하지 않음 |
| reading | 서재·현재 진도·최고 진도·독서 기록·통계 | 판본 정보를 직접 수정하지 않음 |
| wiki | 공개 위키·초안·관계·제출본·검수·이미지 참조 | 검수와 공개 반영의 일관성 유지 |
| credit | 지갑·예약·차감·지급·회수·복구 | 토큰의 실제 증감과 중복 방지 책임 |
| ai | 질문·대화·관계도·작업·스트리밍 이벤트 | 다른 모듈의 공개 기능을 사용해 범위·토큰 확인 |
| notice | 공지사항 | 사용자 조회와 관리자 관리 포함 |
| account-lifecycle | 회원가입 완료와 탈퇴의 전체 진행 | 여러 모듈의 기능을 조합하며 데이터를 직접 대신 수정하지 않음 |

관리자 기능은 별도의 거대 업무 모듈로 모으지 않는다. 관리자 위키 검수는 wiki, 관리자 토큰 조정은 credit에 둔다.

## 6. 모듈 내부 구성

주요 업무 모듈은 다음 역할로 구분한다. 각 역할을 Gradle 하위 모듈로 분리하여 의존성을 관리한다. 필요한 역할만 만들며 내용이 없는 모듈을 형식적으로 생성하지 않는다.

| 구성 | 쉽게 설명하면 | 포함하는 코드 |
| --- | --- | --- |
| contract | 다른 업무가 사용할 수 있는 공개 기능 | 호출 인터페이스, 전달·반환 데이터 |
| domain | 해당 업무에서 지켜야 할 규칙 | 업무 모델, 값 객체, 상태 변화·검증 규칙 |
| application | 한 기능을 수행하는 순서 | 조회·검증·변경의 흐름, 트랜잭션, 저장·외부 연결 인터페이스 |
| adapter-web | HTTP와 내부 기능을 연결하는 입구 | Controller, 요청·응답 형식, 입력 검증 |
| adapter-persistence | DB에 저장하고 읽는 구현 | JPA Entity·Repository, 업무 모델과 DB 모델 변환 |
| adapter-integration | 외부 서비스를 호출하는 구현 | 카카오·메일·도서 검색·LLM 연결 |
| adapter-worker | 백그라운드 작업을 시작하는 입구 | 작업 수신·스케줄 실행 연결 |

여기서 인터페이스는 “무슨 기능을 제공하는지”를 약속하고, 구현체는 “실제로 어떻게 처리하는지”를 담당한다. application은 저장 인터페이스를 사용하고 adapter-persistence가 DB 처리 방법을 제공한다.

예를 들어 토큰 모듈은 다음과 같이 나뉜다.

| 위치 | 역할 예시 |
| --- | --- |
| credit:contract | 토큰 예약 요청과 결과를 공개 |
| credit:domain | 가용 잔액보다 많이 예약할 수 없다는 규칙 |
| credit:application | 지갑 조회, 규칙 적용, 예약 저장의 순서 |
| credit:adapter-persistence | 실제 DB 조회·잠금·저장 |
| credit:adapter-web | 잔액과 거래 이력 조회 API |

## 7. 모듈 의존 규칙

의존한다는 것은 다른 모듈의 코드를 가져다 사용한다는 뜻이다. 호출 편의를 위해 경계를 넘기보다, 필요한 공개 기능을 정의하여 사용한다.

| 규칙 | 적용 예시 |
| --- | --- |
| 다른 업무에는 contract를 통해 접근한다 | AI는 credit의 토큰 예약 기능을 호출 |
| 다른 업무의 Repository·JPA Entity를 직접 사용하지 않는다 | AI가 토큰 테이블을 직접 수정하지 않음 |
| domain은 웹·DB 기술에 의존하지 않는다 | 업무 규칙에 Controller, JPA 어노테이션을 넣지 않음 |
| application은 adapter 구현을 직접 참조하지 않는다 | 저장 인터페이스를 통해 DB 접근 |
| contract는 내부 구현 타입을 공개하지 않는다 | JPA Entity 대신 필요한 결과 데이터 반환 |
| domain 모델과 DB 모델을 분리한다 | 업무 규칙 변경과 테이블 매핑을 구분 |
| 순환 의존을 허용하지 않는다 | 서로의 서비스가 끝없이 호출하거나 Bean 생성이 순환하지 않게 구성 |
| 실행 모듈은 조립과 설정을 담당한다 | API 서버의 시작 클래스 주변에 업무 규칙을 몰아넣지 않음 |

Gradle 의존성 설정과 아키텍처 테스트로 규칙을 확인한다. 인터페이스를 사용하더라도 실제 호출이 순환할 수 있으므로 런타임 구성도 함께 점검한다.

여러 업무가 연결되는 기능은 처리 순서를 맡는 곳을 명확히 한다.

| 기능 | 진행 책임 | 함께 사용하는 업무 |
| --- | --- | --- |
| 회원가입 완료 | account-lifecycle | identity, member, terms, credit |
| 회원 탈퇴 | account-lifecycle | 개인정보를 소유한 각 모듈 |
| 검수 승인·보상 | wiki | wiki, credit |
| AI 질문 접수·완료 | ai | reading, wiki, credit 등 |

공통 지원 코드에는 응답 형식·로그·파일 저장·메시지 전달 등 기술적인 기능을 둔다. 회원·위키·토큰의 업무 규칙을 common 같은 공통 모듈로 옮겨 의존성 문제를 피하지 않는다.

## 8. 데이터와 API 규칙

### 8.1 데이터 관리

- 각 업무 모듈이 자신의 데이터와 저장 코드를 소유한다.
- 다른 업무와의 연결은 회원 ID·도서 ID 같은 식별자를 기본으로 사용한다. 모듈 간 JPA 객체 연결은 만들지 않는다.
- 같은 DB를 사용한다는 이유로 다른 모듈의 테이블을 직접 변경하지 않는다.
- 반드시 함께 성공해야 하는 변경은 함께 확정한다. 예를 들어 검수 승인만 되고 보상이 누락되는 상태를 방지한다.
- 외부 AI·메일 호출이 끝날 때까지 DB 트랜잭션과 잠금을 오래 유지하지 않는다.
- DB 구조 변경은 마이그레이션 파일로 기록한다. 운영 DB를 개발자마다 수동 변경하거나 애플리케이션 자동 생성 기능으로 관리하지 않는다.

### 8.2 API 계약

- 기본 경로는 `/api/v1`, JSON 필드는 camelCase를 사용한다.
- 공통 성공·오류 응답, 페이지네이션, 날짜·시간 표현을 통일한다.
- 사용자 ID는 인증 정보에서 확인한다. 요청에 포함된 다른 사용자의 ID를 믿고 권한을 부여하지 않는다.
- 인증 여부뿐 아니라 해당 초안·대화·이미지의 소유권도 확인한다.
- 반복 요청으로 중복 가입·검수·과금이 발생하지 않도록 한다. 이를 멱등성이라고 하며, API 명세의 Idempotency-Key 규칙을 적용한다.
- 동시에 편집한 내용을 덮어쓰지 않도록 버전을 확인한다. API 명세의 ETag·If-Match 규칙을 적용한다.
- 공개 위키의 기준 버전과 초안 편집 버전은 별도로 관리한다.
- 경로·필수 필드·응답 구조·오류 의미를 바꾸면 관련 프론트엔드와 협의하고 명세를 함께 갱신한다.

### 8.3 백그라운드 작업

- AI 작업은 서버가 재시작되어도 상태를 확인하고 복구할 수 있어야 한다.
- 작업 접수와 worker 전달이 누락되지 않게 하고, 같은 작업이 여러 번 전달될 수 있음을 고려한다.
- 결과 저장·차감·복구는 같은 작업에 대해 한 번만 반영한다.
- 스트리밍 연결이 끊겨도 작업 상태와 결과를 다시 확인할 수 있어야 한다.
- 결과 저장 시에도 탈퇴 여부와 작업 유효성을 다시 확인한다.

## 9. 협업과 변경 관리

### 9.1 기능을 개발할 때

기능을 맡으면 먼저 요구사항과 API 계약을 확인하고, 어느 업무가 데이터와 처리를 책임지는지 정한다. 다른 모듈에 필요한 기능이 없다면 내부 저장 코드에 접근하지 않고 공개 인터페이스를 협의한다.

기능 개발에는 요청 처리, 업무 규칙, 저장, 실패 처리, 필요한 테스트를 함께 포함한다. 외부 서비스의 키가 없어 대체 구현으로 검증한 경우 실제 연동까지 완료한 것으로 표시하지 않는다.

### 9.2 변경 전에 공유할 사항

다음 변경은 관련 담당자와 협의하고 결정 이유를 기록한다.

- 서비스 정책: 가입 조건, 공개 범위, 토큰 비용, 삭제 범위 등.
- API 계약: 경로, 필수 입력, 응답 형식, 오류 의미 등.
- 모듈 경계: 데이터 소유권 이동, 새로운 모듈 의존성 등.
- 운영 구조: DB 종류, 작업 전달 방식, 외부 공급자 등.

기술 선택은 간단한 설계 결정 기록으로 남긴다. 무엇을 선택했고 왜 선택했는지, 어떤 제약이 있는지면 충분하다. 라이브러리 버전과 실행 환경은 저장소 설정을 기준으로 맞추고 개발자별로 다르게 관리하지 않는다.

### 9.3 코드 검토 기준

- 변경 이유와 사용자에게 달라지는 동작이 명확한가?
- 해당 기능이 올바른 모듈에 있으며 내부 경계를 지켰는가?
- 권한·스포일러 범위·개인정보 정책이 적용되는가?
- 실패하거나 요청이 겹쳐도 데이터와 토큰이 일관되는가?
- API·DB 변경과 관련 문서가 함께 갱신되었는가?
- 실제로 실행한 테스트와 아직 확인하지 못한 부분이 구분되는가?

## 10. 기능 완료 기준

기능은 코드가 존재하는 것만으로 완료되지 않는다. 다음 사항을 확인한 뒤 완료로 판단한다.

| 확인 영역 | 완료 기준 |
| --- | --- |
| 정상 동작 | 명세의 입력·처리·응답이 연결되어 실제로 동작함 |
| 예외·권한 | 잘못된 입력, 타인 데이터 접근, 만료·실패 상황을 처리함 |
| 데이터 | 저장·수정·삭제와 마이그레이션이 검증됨 |
| 중복·동시성 | 가입 보상, 진도, 검수, 토큰 등 중요한 경합을 검증함 |
| 모듈 구조 | 허용된 의존 방향과 데이터 소유권을 지킴 |
| 실행 | 관련 실행 앱이 필요한 설정으로 정상 시작됨 |
| 문서 | API 계약·실행 방법·남은 제약이 실제 구현과 일치함 |

특히 최고 진도 증가분, 스포일러 노출, 중복 차감·보상, 탈퇴 후 데이터 재생성은 반드시 회귀 테스트 대상으로 유지한다. 테스트를 실행하지 못했다면 통과한 것으로 기록하지 않는다.

비밀번호·인증 토큰·인증번호·외부 서비스 비밀키는 코드와 로그에 남기지 않는다. 운영 지표와 오류 추적에 필요한 정보도 개인정보 최소화 원칙에 맞춰 기록한다.
